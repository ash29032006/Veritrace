# Indexing evidence

Generated by `npm run bench:indexes` on 2026-10-11, PostgreSQL undefined.

The demo dataset (66 batches) is far too small for indexes to matter: every table fits in a page
or two and the planner correctly prefers sequential scans. The benchmark therefore builds a separate
database with the same schema at a realistic size, measures five hot-path queries with
`EXPLAIN (ANALYZE, BUFFERS)` **before** `04_indexes.sql` exists, creates the indexes, and measures again.
Each query runs 7 times; the table shows the median execution time.

## Dataset

| table | rows |
|---|---:|
| outlet | 2,000 |
| batch | 20,000 |
| batch_composition | 31,996 |
| shipment | 50,000 |
| audit_log | 1,00,000 |
| shipment_line | 2,04,984 |
| inventory | 2,04,468 |

## Results

| query | index that serves it | before (ms) | after (ms) | speed-up | plan after |
|---|---|---:|---:|---:|---|
| Forward exposure (recursive CTE), the query behind every recall | `idx_shipment_line_batch` | 33.98 | 0.36 | 95.4x | Index Only Scan using pk_batch_composition, Index Scan using idx_shipment_line_batch, Index Scan using shipment_pkey |
| Backward provenance (recursive CTE) | `idx_bc_child` | 7.44 | 0.03 | 248.0x | Index Scan using idx_bc_child |
| Recall quarantine lookup: every outlet holding the affected batches | `idx_inventory_batch` | 7.91 | 0.02 | 439.2x | Bitmap Index Scan |
| Latest shipments to one outlet | `idx_shipment_outlet` | 1.09 | 0.01 | 83.8x | Bitmap Index Scan |
| Audit log, newest page filtered by action | `idx_audit_performed_at (newest first, filter applied while walking it)` | 5.13 | 0.01 | 427.7x | Index Scan using idx_audit_performed_at |

Primary keys already index their leading column, so the forward step of the recursive CTE
(`batch_composition.parent_batch_id`) was fast even before; the new indexes cover the lookups
the primary keys cannot: by `batch_id` on `shipment_line` and `inventory`, by `child_batch_id`
for provenance, by outlet for history, and by action and time for the audit log.

## Forward exposure (recursive CTE), the query behind every recall

```sql
WITH RECURSIVE downstream (batch_id) AS (
    SELECT 37::bigint
    UNION
    SELECT bc.child_batch_id FROM batch_composition bc
      JOIN downstream d ON d.batch_id = bc.parent_batch_id
)
SELECT DISTINCT o.outlet_id, d.batch_id, s.shipment_id, sl.quantity
  FROM downstream d
  JOIN shipment_line sl ON sl.batch_id = d.batch_id
  JOIN shipment s ON s.shipment_id = sl.shipment_id
  JOIN outlet o ON o.outlet_id = s.outlet_id
```

## Backward provenance (recursive CTE)

```sql
    SELECT parent_batch_id FROM batch_composition WHERE child_batch_id = 19993
    UNION
    SELECT bc.parent_batch_id FROM batch_composition bc
      JOIN upstream u ON u.batch_id = bc.child_batch_id
)
SELECT COUNT(*) FROM upstream
```
